# Burmalda · Privacy Demo

Автономный MVP приватных ставок и контролируемого раскрытия документов. Настоящие AES-256-GCM, Ed25519, RSA-OAEP и разделение ключа по Шамиру «2 из 3». Только синтетические данные и условные деньги.

**Основная гарантия модели:** выгрузки базы ЦУПИС вместе с его собственной долей недостаточно для открытия документов. У каждого клиента индивидуальный ключ. Открытие одной записи не открывает архив остальных клиентов.

## Запуск

Нужен Python 3.12+ и зависимости:

```bash
python -m pip install -r requirements.txt
python run_demo.py
```

Откройте **http://127.0.0.1:5000**. Можно также запускать `python app.py`.

На Windows: `./Start-Demo.ps1`. Если на компьютере уже настроен Documents launcher для WSL, скрипт использует его; иначе — установленный Python. Зависимости устанавливайте выбранным интерпретатором.

Стенд запускает семь дочерних процессов и панель наблюдателя. `Ctrl+C` завершает все запущенные им процессы. Перезапуск сохраняет данные. Очистка синтетических данных — через кнопку сброса в панели.

Если порты заняты:

```bash
python run_demo.py --port 5050 --service-base 5201
```

Все интерфейсы привязаны к loopback. Не публикуйте этот демонстратор в интернете и не загружайте настоящие документы.

## Показ за 5–10 минут

1. **Регистрация.** Создайте вымышленного игрока. Посмотрите отдельный AES-архив в ЦУПИС и метаданные трёх долей.
2. **Приватная ставка.** Примите ставку в Alpha. У букмекера появятся псевдоним, событие, сумма и подписанная квитанция. Документов нет. При желании повторите в Beta: псевдоним будет другим.
3. **Расчёт.** В шаге ставки нажмите «Рассчитать событие». Условные холды будут рассчитаны, игровой отчёт уйдёт получателю. Второе событие не затрагивается.
4. **Одна доля.** Нажмите «Проверить одну долю». Код восстановления возвращает `INSUFFICIENT_SHARES`. Панель не запрашивает другие доли.
5. **Запрос.** Выберите цель, контекст БК и поля. По умолчанию паспорт не передаётся.
6. **Подтверждение.** В клиентском окне показаны адресат, поля и версия. Одобрение подписывается ключом клиента. Альтернативный путь — арбитр; отказ действительно блокирует выдачу его доли.
7. **Доставка и ротация.** Получатель получает выбранные поля, все хранители — новые доли. Тест AES-GCM проверяет, что старый ключ не открывает новую запись. В матрице видимости и инспекторе сравните роли.

Сырые доли и приватные ключи панель не выдаёт. Инспектор показывает разрешённые проекции фактического состояния, а не прямую выгрузку всех таблиц.

## Участники

| Процесс | Собственное хранилище | Назначение |
| --- | --- | --- |
| wallet | `.runtime/wallet/` | Документы самого клиента, пользовательские ключи, доля №1, квитанции |
| cupis | `.runtime/cupis/` | Зашифрованный архив, доля №2, соответствия псевдонимов, условные счета |
| arbiter | `.runtime/arbiter/` | Доля №3, проверка демонстрационного основания, решения |
| bookmaker_alpha / bookmaker_beta | Разные каталоги | Собственные котировки и ставки по собственным псевдонимам |
| recipient | `.runtime/recipient/` | Игровые отчёты и разрешённые поля раскрытия |
| disclosure | `.runtime/disclosure/` | Контекст раскрытия, зашифрованная очередь доставки и статусы ротации |
| observer | `.runtime/observer/` | Привилегированная локальная панель, ключ её сервисной подписи |

Каждый процесс использует **одну свою SQLite-базу** и собственные приватные ключи. Общий реестр содержит только открытые ключи и адреса. Сервисы обмениваются подписанными и адресно зашифрованными HTTP-сообщениями; имена ролей в JSON сами по себе не предоставляют полномочий.

## Протокол раскрытия

1. ЦУПИС создаёт ограниченный запрос: запись, версия ключа, адресат, поля, цель и срок.
2. Клиент или арбитр подписывает именно этот запрос; компонент проверяет подпись и владельца доли.
3. Компонент получает долю ЦУПИС, восстанавливает индивидуальный ключ в памяти и открывает запись.
4. Формирует адресно зашифрованный результат для получателя и новый архив с новым случайным ключом.
5. В **одной локальной транзакции** сохраняет план продолжения и зашифрованные для владельцев новые доли. Полные ключи и открытая запись в этот план не попадают.
6. Получатель подтверждает доставку; все три владельца сохраняют новые доли.
7. ЦУПИС переключает активную версию; старые рабочие доли удаляются. При сбое доступна команда «Продолжить доставку и ротацию», в том числе после перезапуска компонента раскрытия.

Сетевые сообщения и отчёты шифруются случайным AES-ключом; ключ шифруется RSA-OAEP/SHA-256 открытым ключом адресата. Подпись Ed25519 связывает сообщение с заранее зарегистрированным отправителем. AES-GCM использует AAD для привязки записи к клиенту, ключу и версии.

## Проверки

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q tests
```

Тесты запускают отдельные реальные процессы в временных каталогах. Проверяются пары долей, смешение клиентов и версий, повторяющиеся индексы, целостность AES-GCM, доступ между ролями, подмена подписанного сообщения и согласия, отрицательные суммы, повтор ставки, конкурентное списание, расчёт по событию, отказ арбитра, отзыв допуска, ограничение полей, ротация и продолжение после сбоя получателя/перезапуска раскрытия.

## Границы MVP

- Это демонстратор разделения секрета и контролируемого раскрытия, **не реализация вычислительного SMPC** и не распределённое AES-расшифрование без восстановления ключа.
- Шамир «2 из 3» допускает любую пару долей, включая клиент + арбитр при наличии шифротекста. Приложение показывает пути ЦУПИС + клиент и ЦУПИС + арбитр.
- Реализация Шамира на GF(256) проверена тестами, но не проходила независимый криптографический аудит.
- Все процессы находятся на одном компьютере и под одним владельцем ОС. От администратора, способного прочитать все каталоги, изоляции нет. Bootstrap создаёт все сервисные ключи локально; это не независимые организации или HSM.
- ЦУПИС видит исходные документы при идентификации. Компонент раскрытия временно видит полный ключ и запись; получатель может сохранить разрешённый результат.
- Сговор двух хранителей, накопление долей и компрометация во время раскрытия не предотвращаются самим Шамиром.
- Ротация не отзывает раскрытые данные. Сохранённый старый шифротекст можно открыть сохранённым старым ключом. Удаление рабочих записей и Python-переменных не доказывает стирание копий из памяти, файловой системы или резервных копий.
- Журналы содержат метаданные; хэш-цепочки локальные, без внешнего закрепления. Реальные KYC, платежи, суды и регуляторные процессы имитируются.
- Кошелёк — отдельный локальный процесс стенда, а не независимо защищённое мобильное приложение. Панель наблюдателя имеет привилегированный обзор и управление синтетическими участниками.
- Нагрузка, отказоустойчивость промышленного уровня и соответствие законодательству не подтверждены. Права на промышленную коммерческую поставку требуют отдельного согласования.

Активная реализация находится в `burmalda/`. Ветка основана на `algorythm` (`aeef836`); прежний монолитный запуск заменён новым стендом. Существующие ветки не изменяются.

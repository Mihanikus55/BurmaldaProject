# BurmaldaProject — четыре сервиса на FastAPI

Приватные ставки: букмекер видит ставку и не видит человека, центр Бурмалда
видит шифротекст и не видит ни человека, ни ставок, регулятор после расчёта
события собирает всё вместе.

## Сервисы

| Порт | Сервис | Кто | База |
|---|---|---|---|
| 8001 | `services/client_app.py` | Телефон клиента | `data/client_app.db` |
| 8002 | `services/burmalda.py` | Центр Бурмалда | `data/burmalda.db` |
| 8003 | `services/bookmaker.py` | БК Альфа | `data/bookmaker_bk_alpha.db` |
| 8005 | `services/bookmaker.py` | БК Бета | `data/bookmaker_bk_beta.db` |
| 8004 | `services/regulator.py` | Регулятор | `data/regulator.db` |
| 8090 | `ui/index.html` | Интерфейс | — |

У каждого сервиса **своя** база SQLite отдельным файлом. Это не для удобства:
смысл схемы в том, что ни одна сторона не владеет полной картиной, и общая
база обнулила бы всю конструкцию.

Букмекер — один и тот же файл, поднятый дважды с разным `BOOKMAKER_ID`.
Второй экземпляр нужен, чтобы было видно главное свойство: у двух контор
лежат разные токены одного человека, и связать их они не могут.

## Как поднять

```bash
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python3 run_all.py                 # поднять все процессы и интерфейс
python3 stop_all.py                # остановить
```

На Windows — то же самое, только `python` вместо `python3` и
`.venv\Scripts\activate` вместо `source .venv/bin/activate`.
Скрипты `run_all.py` и `stop_all.py` работают на всех системах;
`run_all.sh` и `stop_all.sh` оставлены для macOS и Linux.

Полезные ключи:

```
python3 run_all.py --fresh           начать с чистых баз
python3 run_all.py --ui-port 9100    если 8090 занят
python3 stop_all.py --clean          остановить и удалить базы
```

## Базы

Лежат в `data/`, по файлу на сервис: `client_app.db`, `burmalda.db`,
`bookmaker_bk_alpha.db`, `bookmaker_bk_beta.db`, `regulator.db`.
Папка создаётся сама при первом запуске.

Почистить, не останавливая сервисы, — кнопка **«Сброс»** на странице или
клавиша `R`: она дёргает `POST /reset` у всех сервисов. Начисто, с
удалением файлов, — `python3 stop_all.py --clean`.

Две страницы:

- **http://127.0.0.1:8090** — для защиты. Крупно, один шаг за раз, листается
  пробелом. Семь шагов примерно на две минуты. Активные карточки подсвечены,
  остальные гаснут — показывать пальцем или указкой ничего не нужно.
- **http://127.0.0.1:8090/log.html** — журнал. Читается сверху вниз как
  рассказ: этап, кто что сделал, что именно поехало и что из этого видно.
  Листается пробелом, удобно снимать скриншоты по кускам.
- **http://127.0.0.1:8090/detail.html** — подробная, со всеми таблицами баз,
  формами и ручными кнопками. Для работы и для вопросов после доклада.

Сквозной прогон в консоли, без браузера: `python3 demo.py`

Порт интерфейса — 8090, а не 8080: восьмитысячный часто занят Tomcat или
Jenkins. Если 8090 тоже занят: `UI_PORT=9100 ./run_all.sh`

Обе страницы — обычная статика, раздаётся `python3 -m http.server`. Логики в
них нет: они опрашивают `GET /db` каждого сервиса и показывают содержимое
четырёх баз как есть. Все кнопки — вызовы тех же эндпоинтов, что дёргает
`demo.py`.

Логи каждого сервиса — в `logs/<имя>.log`. Если какой-то порт не поднялся,
смотреть туда.

Вручную по одному:

```bash
python3 -m uvicorn services.regulator:app  --port 8004 --reload
python3 -m uvicorn services.burmalda:app   --port 8002 --reload
BOOKMAKER_ID=bk_alpha python3 -m uvicorn services.bookmaker:app --port 8003 --reload
BOOKMAKER_ID=bk_beta  python3 -m uvicorn services.bookmaker:app --port 8005 --reload
python3 -m uvicorn services.client_app:app --port 8001 --reload
```

Swagger у каждого сервиса: `http://127.0.0.1:<порт>/docs`

## Эндпоинты

У каждого сервиса есть `GET /db` — полный дамп его базы (интерфейс будет
опрашивать именно их) и `POST /reset`.

**Телефон клиента (8001)**
```
POST /kyc                {full_name, passport, birth_date}      -> разблокировка
POST /tokens/generate    {bookmakers: ["bk_alpha","bk_beta"]}   -> этап 1
GET  /events?bookmaker_id=bk_alpha
POST /bet                {bookmaker_id, event_id, selection, stake}  -> этап 2
```

**Центр Бурмалда (8002)**
```
POST /kyc/verify         {full_name, passport, birth_date}
POST /register           {token, bookmaker_id, pd_blob, share_a}
GET  /try-read/{token}   «попробовать прочитать архив»
```

**Букмекер (8003 / 8005)**
```
GET  /events
POST /bet                {token, event_id, selection, stake, share_b}
POST /settle             {event_id, outcome}                    -> этап 3
POST /report             логи и доля Б -> напрямую регулятору
GET  /try-read/{token}
```

**Регулятор (8004)**
```
POST /registry           от Бурмалды: {token, bookmaker_id, pd_blob, share_a}
POST /report             от букмекера: {token, bookmaker_id, bets, share_b}
POST /aggregate          этап 4: соединить таблицы, собрать ключ, расшифровать
GET  /try-read/{token}
```

## Этапы

**1. Регистрация.** Клиент приходит в центр, Бурмалда сверяет его с реестром,
проверяет 18+ и самозапрет, разблокирует приложение. Телефон для каждого
букмекера генерирует токен и ключ AES-256, шифрует ФИО и паспорт, режет ключ
XOR на две доли и **стирает ключ**. Токен, шифротекст и доля А уходят в
Бурмалду, та пересылает их регулятору и долю А у себя обнуляет.
Доля Б остаётся на телефоне.

**2. Ставка.** Клиент подтверждает ставку и вместе с ней отдаёт букмекеру
долю Б. Букмекер видит только токен.

**3. Расчёт.** Считает букмекер. Логи ставок и долю Б он отправляет
**напрямую регулятору**, минуя Бурмалду.

**4. Агрегация.** Регулятор соединяет две таблицы по токену, складывает доли
XOR, получает ключ и расшифровывает личность.

## Что это даёт

- Букмекер не узнаёт личность никогда: доля у него есть, шифротекста нет.
- Бурмалда не узнаёт личность никогда: шифротекст есть, но доля Б через неё
  не проходит ни на одном шаге.
- Регулятор раскрывает **только тех, кто реально играл**. У неигравшего
  клиента доля Б осталась на телефоне, и его архив не открыть.
- Утечка любой одной базы не даёт ничего.

**Граница, которую проект не переходит:** при проверке на входе Бурмалда
видит ФИО и паспорт — иначе проверить их нельзя. В базу она их не пишет, но
это обещание процедуры, а не математики. И после этапа 4 регулятор знает
личность полностью и навсегда — доли больше ничего не защищают.

## Криптография

Вся в `common/crypto.py`, её немного:

- **AES-256-GCM** — шифрование персональных данных, только на телефоне.
  GCM заверяет шифротекст: правка хотя бы одного бита ломает расшифрование.
- **XOR, «2 из 2»** — разделение ключа. Одна доля это равномерный случайный
  мусор: о ключе по ней не известно ровно ничего.

Подписей нет: договорились, что разблокированное приложение означает
доверенного клиента, и букмекеру проверять нечего.
